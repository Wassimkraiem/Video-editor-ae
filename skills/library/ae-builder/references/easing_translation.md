# Easing translation: make the AE keys move exactly like the MP4

## Why the first rebuild felt wrong (measured)

The source reel used a spring for every pop: `1 - e^(-5u) * cos(8u)` over a "duration" of 0.65 s.
The AE rebuild put 2 keys 0.65 s apart (0 to 100%) and added a generic bounce expression after the second key.

| | Reaches 100% | Peak | Settled |
|---|---|---|---|
| MP4 spring | 0.13 s | 117% at 0.21 s | 0.57 s |
| AE rebuild | 0.65 s | 112% at 0.73 s | 1.19 s |

Max difference: 70% of the move. Every pop arrived 5x late and floated.
Root cause: a spring's "duration" is its settling window, not its travel time. It crosses the target at about 20%
of that window and spends the rest overshooting and settling. Mapping duration -> key span is wrong for any
overshooting curve. A second cause: one global bounce (fixed 20% / 2.5 Hz / decay 5) was bolted onto every key that
arrived with speed, regardless of what the source did.
A third: no motion blur on layers, while the MP4 blended 10 sub-frames per frame, so AE looked steppier.

## The rule

Keys must reproduce the source curve, verified by numbers, within 2% of the move at every frame and motion-blur
sub-frame, and within 1 frame of timing. Not "similar ease". Not a preset that looks close.

## Method

1. **Get the real curve per channel.** From the generating code read the exact function, start and length of every
   move: scale, position, rotation and opacity of the same entrance are separate channels (they often share a curve
   but not always: opacity was linear over the first 29% in the reel). If only an MP4 exists, track the element and
   use `fit_samples()` on the tracked values.
2. **Fit with `scripts/ease_fit.py`, frame-aware.** `fit_move(f, t0, dur, fps)`:
   - keys only on whole frames (the first key is the last frame at or before the start, the last key the first frame
     at or after the end),
   - turning points (overshoot peak, undershoot dip) become real keys, so the overshoot is visible and draggable,
   - each key gets the source's own speed at that moment; influences are searched until the AE bezier matches the
     source at every frame and 4 sub-frames per frame,
   - if a segment is still over 2%, a key is added at its middle frame and the fit is redone.
   Blended channels (camera punch times drift, a squash chain, anything not a textbook ease) use
   `fit_samples(times, values)` on the channel sampled from the code.
3. **Emit the fits as data** in the build script (`var FITS = {...}`) and apply with `applyFit(layer, channel, FITS.x, from, to)`.
   All channels of one move use their own fit but the same start and end frames.
4. **Verify** after the dry-run: `DUMP_KEYS=keys.json node ae_mock_dryrun.js Build.jsx`, then
   `python3 verify_curves.py keys.json checks.json`. One check per move type (at least every distinct curve, and
   every move under 0.3 s or with gravity). Any BAD = fix before delivering.
5. **Match motion blur**: layer motion-blur switch on for everything that moves; comp shutter angle = source shutter
   (sub-frames spread over half a frame = 180 deg), phase = -angle/2, 16 samples, adaptive limit 128 (`matchMotionBlur`).

## Never

- Never use a curve's nominal duration as the key span for springs or back-eases.
- Never add a generic bounce/inertia expression on top of keys to "fake" an overshoot. Overshoot is keys.
- Never hide timing curves inside expressions (`Math.pow(1 - p, 3)`, `1 - Math.exp(-5 * p) * Math.cos(8 * p)`): the
  designer can't see or edit them. Curves live in keyframes; expressions only map, offset and combine.
- Never guess speed/influence from a feeling ("out = 3x, 33%"). Fit it.

## When an expression IS the right tool for an overshoot

Reaction systems (things that bounce because something else hit them) may use a bounce expression, but with
designer-facing controls and no fixed numbers:

```js
// OVERSHOOT: after this layer's last arrival key it overshoots and settles. Controls: CTRL_Motion > Overshoot (%), Bounces per Second, Settle Time (s).
var c = thisComp.layer("CTRL_Motion");
var over = c.effect("Overshoot (%)")("Slider") / 100;          // 17 = the source spring
var hz = c.effect("Bounces per Second")("Slider");             // 1.96 for a 0.65 s spring (8 / (2 pi 0.65))
var settle = Math.max(0.05, c.effect("Settle Time (s)")("Slider"));   // time until the wobble is under 1%
var v = value;
if (numKeys > 1) {
  var n = nearestKey(time).index; if (key(n).time > time) n--;
  if (n > 1) {
    var t = time - key(n).time, w = 2 * Math.PI * hz, k = 4.6 / settle;
    var tp = Math.atan(w / k) / w, peak = Math.sin(w * tp) * Math.exp(-k * tp);   // so the first bump equals Overshoot exactly
    var move = sub(key(n).value, key(n - 1).value);
    if (t > 0) v = add(v, mul(move, over * Math.sin(w * t) * Math.exp(-k * t) / peak));
  }
}
v;
```

Exact equivalence (useful when the source is a damped spring `1 - e^(-a u) cos(b u)` over D seconds): put the arrival
key where the spring first crosses the target (u0 = pi / 2b), with arrival speed `move * e^(-a u0) * b / D`; after it
the residual is exactly `(speed / w) sin(w t) e^(-k t)` with `w = b / D` and `k = a / D`.
